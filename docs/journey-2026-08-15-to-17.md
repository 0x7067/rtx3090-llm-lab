# Qwen3.8-27B on one RTX 3090: what we changed and why

A self-contained account of three days of work on the `qwen3.8-27b` model backend,
from 2026-08-15 to 2026-08-17. It covers the quantization comparison, the decode-speed
campaign that followed, and the decision not to fine-tune the model.

You do not need any other document to read this one. Every number quoted here is
reproduced in the text.

The day after this account closes is written up separately in
`docs/journal-2026-08-17.md`, which covers patch 0007, the truncated drafter, and stacked
n-gram drafting in image v11. `docs/PERFORMANCE.md` is the kernel-campaign write-up this
document narrates.

## Result

Decode speed on the greedy benchmark, from the pre-campaign baseline to the shipped
image `llama:cuda-swap-v10` with `--spec-draft-n-max 5`:

| workload | before | now | change |
|---|---:|---:|---:|
| 54k-token agentic decode | 49.8 t/s | 69.3 t/s | +39% |
| ~1k-token code prompt | 64.0 t/s | 84.1 t/s | +31% |
| short prompt (~43 tokens) | 62.4 t/s | 72.4 t/s | +16% |

All six numbers come from the greedy benchmark: `temperature 0, top_k 1, seed 42,
cache_prompt true`. Production samples at `--temp 1.0 --top-k 20 --top-p 0.95`, where
every arm measures lower, including production's own. The ranking holds; the absolute
values do not. Compare these numbers only with each other.

Read each row as a chain, not as one measurement. No single benchmark block spans the
whole campaign. Each row joins two or three same-block comparisons taken on successive
images, and this document warns elsewhere against comparing across blocks. The joins
are close where they overlap — 70.33 against 70.5 t/s on `mid1k`, 68.50 against 68.4 on
`short`, 66.8 against 66.8 on `deep` — so the chains are sound, but treat the end-to-end
percentages as approximate and trust the per-stage numbers below them.

The quantization change of 2026-08-15 is a separate result on a separate methodology. It
gave +1.5% warm throughput and saved 842 MiB of VRAM. Do not add it to the table above.

Nobody fine-tuned the model. Fine-tuning does not raise tokens per second, and this host
cannot train a 27B model. See "Fine-tuning" below.

The gains came from three CUDA kernel patches and one configuration change. They did not
come from the speculative-decoding settings that looked like the obvious place to start.
The configuration change only works because one of the kernel patches landed first.

## The model and the machine

**Hardware.** One RTX 3090, 24,564 MiB of VRAM, compute capability 8.6, 82 streaming
multiprocessors, 370 W cap. The host has 20 threads and 62 GB of RAM.

Being an Ampere card decides much of what follows. Several llama.cpp fast paths for a
quantized KV cache are gated on compute capability 8.9 or higher, which is Ada
Lovelace. They do not exist on this card, so this GPU takes slower code paths that
newer cards avoid.

**Serving.** A single-node k3s cluster runs one Flux-reconciled Deployment of
[`llama-swap`](https://github.com/mostlygeek/llama-swap). llama-swap holds exactly one
`llama-server` process in VRAM at a time and selects it by the request's `model` field.
Four backends share the GPU this way: `qwen3.8-27b`, `muse-glimmer-30b`,
`hauhau-gemma4-26b-a4b`, and `qwen3.6-27b`. All four run at 131,072 tokens of context.
The pod is limited to 12 CPUs, 32 GiB of RAM, and 1 GPU.

**The tuning target.** `qwen3.8-27b` is a hybrid Gated-DeltaNet model: 64 layers, of
which only 16 hold a standard attention KV cache, 24 query heads, 4 key/value heads, and
a head dimension of 256. Six query heads share each key/value head. At `q4_0` the cache
costs 18,432 bytes per token, which is why a 131,072-token window fits at all. The
backend also loads a Q8_0 vision projector and a separate Q4_0 MTP draft model.

Everything must stay resident together. The working VRAM ceiling is 23,400 MiB. The
shipped configuration measured 23,318 MiB in production at draft length 4.

**The shipped command.**

```
/usr/local/bin/llama-server
  -m /models/Qwen3.8-27B-Q4_K_L.gguf
  --mmproj /models/mmproj-Qwen3.8-27B-Q8_0.gguf
  --host 0.0.0.0 --port ${PORT}
  --ctx-size 131072 --predict 131072
  --threads 8 --threads-batch 8 --parallel 1
  --batch-size 512 --ubatch-size 512
  --no-mmap -fa on --jinja
  --cache-type-k q4_0 --cache-type-v q4_0
  --cache-type-k-draft q4_0 --cache-type-v-draft q4_0
  --temp 1.0 --top-k 20 --top-p 0.95 --min-p 0.0 --repeat-penalty 1.0
  --model-draft /models/mtp-Qwen3.8-27B-Q4_0.gguf
  --spec-type draft-mtp --spec-draft-n-max 5
  -ngl 99 -ngld 99
```

With two environment variables set on this backend only:

```
GGML_CUDA_MMVQ_NE11_MAX=3
LLAMA_ARG_CHAT_TEMPLATE_KWARGS={"reasoning_effort":"medium"}
```

**Benchmark payloads** used throughout: `short` is 43 to 53 tokens, `mid1k` is a
1,000-token C++ source prompt, `mid1kprose` is a 1,000-token documentation prompt,
`prose7k` is about 7,000 tokens, and `deep` is 54,440 tokens of llama.cpp sources. The
`deep` payload is the workload this host actually serves.

## Stage 1 — choose a better quantization (2026-08-15)

The backend ran ggml-org's Q4_K_M conversion. Two importance-matrix conversions were
tested against it. Each ran with the production Q8 vision projector and the production
separate Q4 MTP draft, on the pinned runtime, build 10349, commit `62bf73d25`. Each
candidate's SHA-256 was verified against the Hugging Face repository tree before it was
loaded.

| candidate | warm throughput | VRAM after text | VRAM after vision |
|---|---:|---:|---:|
| ggml-org Q4_K_M (baseline) | 62.8 tok/s | 23,858 MiB | 23,874 MiB |
| Unsloth UD-Q4_K_XL | 63.9 tok/s (+1.9%) | 22,856 MiB (−1,000) | 22,876 MiB |
| Bartowski Q4_K_L | 63.7 tok/s (+1.5%) | 23,016 MiB (−842) | 23,034 MiB |

The throughput figures use three requests with a 256-token completion cap, discarding
the first, which includes model loading. Cold-load times are excluded, because file
verification and the operating-system page cache made the load conditions unequal.

Both candidates loaded on the existing image without a runtime upgrade. Bartowski
published its files with a newer llama.cpp build than the one deployed, and its main
quantization still loaded. Both candidates returned the exact output marker, produced a
valid structured tool call, scored 10/10 on the deterministic vision suite (shape order,
bar-chart order, and dot count), and retrieved an exact key from a 90,040-token prompt
with thinking disabled.

Bartowski Q4_K_L was promoted behind the existing `qwen3.8-27b` model ID in commit
`31c5270`. It keeps embedding and output tensors at Q8_0, which is a plausible quality
advantage. The Q4_K_M file stays in the model cache as the rollback artifact. Neither
candidate's newer combined-MTP path was tested; both tests kept the production separate
draft, so the comparison measures the quantization alone.

**This was a compatibility gate, not a quality gate.** Neither candidate has been
measured on a real task suite. The planned comparison over at least 100 representative
tasks was never run, so the choice between Bartowski and Unsloth rests on smoke tests
plus an argument about tensor precision. Unsloth saves about 160 MiB more VRAM.

## Stage 2 — find where the time goes (2026-08-16)

The weights are about 17.5 GB. At roughly 850 GB/s a step without speculation should
cost about 21 ms, which sets a ceiling near 48 t/s. The KV cache should be almost free:
32,768 tokens across 16 layers is 604 MB, or 0.76 ms at 800 GB/s.

Measurement disagreed:

| context depth | t/s | ms per token | added against depth 0 |
|---:|---:|---:|---:|
| 0 | 39.54 | 25.29 | — |
| 32,768 | 32.23 | 31.03 | +5.74 |
| 65,536 | 26.94 | 37.12 | +11.83 |

The penalty is 7.2 times the prediction, and it is linear: 11.83 against twice 5.74,
which is 11.47. A fixed overhead cannot explain a linear cost. Three separate code paths
caused it.

**1. The vector kernel reads the cache once per query head.** For this head size,
quantization, and card, llama.cpp sends batch 1 to the vector flash-attention kernel and
batch 2 or more to the MMA_F16 kernel. The branch that would keep small batches on the
vector kernel requires an Ada card and is dead here. The vector kernel gives every query
head its own block, so with six query heads per key/value head it reads and dequantizes
the same K and V six times per step. Bandwidth predicts +0.75 ms at 32k; six times that
is +4.53 ms against +5.74 ms measured, and the difference is dequantization. The kernel
sustains 632 GB/s, so it is not slow. It is redundant, which decided the fix: share the
cache across the group.

**2. Any batch above 1 converts the whole cache.** The MMA_F16 kernel cannot read a
quantized cache, so llama.cpp converts the entire `q4_0` K and V cache to F16 into a
scratch buffer on every flash-attention call, then reads it back. Measured later by
running the same kernel on an F16 cache, which skips the conversion by construction:
543.6 µs per operation, 67% of the attention cost on the verify path, and 8.70 ms per
verify step across the 16 attention layers.

**3. The kernel switch happens three times too late.** Sustained cost of one forward
step at depth 0, by the number of tokens in the step:

| tokens in step | ms per step | marginal ms per extra token |
|---:|---:|---:|
| 1 | 23.48 | — |
| 2 | 26.37 | 2.89 |
| 4 | 39.14 | 6.57 |
| 8 | 62.35 | 6.24 |
| 12 | 40.13 | −5.56 |
| 16 | 40.52 | 0.10 |

These are two straight lines. The MMVQ kernel costs `23.48 + 5.55·(N−1)` up to 8 tokens.
The MMQ kernel costs `35.43 + 0.39·N` from 12 tokens up. The marginal costs differ by a
factor of 14, and a 12-token step finishes 22.2 ms sooner than an 8-token step. The lines
cross at 3.4 tokens. llama.cpp switches at 9, from a flat constant that applies to every
NVIDIA GPU and every quantization type. Verify batches of 4 to 8 tokens were paying 24%
to 38% more than necessary. That, not draft acceptance, was what limited useful draft
lengths.

## Stage 3 — three kernel patches and one configuration change (2026-08-16)

### Patch 0003 — share the cache across the query-head group

The vector kernel now holds a whole query-head group in registers while the query tokens
stay on the grid. One block serves the group, so it reads and dequantizes K and V once,
and the cache stays quantized. Reusing the vector kernel's selection path also removes
the F16 scratch allocation with no extra code.

Two register problems shaped the code. Writing per-thread results with a runtime index
into an otherwise statically indexed register array is invisible at one column, but at
six columns it makes the compiler move the whole array to local memory. Fully unrolling
the inner loop spilled 116 bytes. An unrolled predicated store and a partial unroll give
255 registers and zero spills at every head size and group width.

The first version regressed shallow contexts, because the grid shrinks sixfold and
cannot fill 82 SMs when the cache is short:

| benchmark row | first version against stock |
|---|---:|
| depth 0 | −2.4% |
| depth 512 | −2.3% |
| depth 4,096 | +0.1% |
| depth 32,768 | +9.8% |
| depth 65,536 | +21.0% |

The error bars are ±0.02 to ±0.10, so those regressions are real. The shipped version
adds a device-aware predicate, shared by the kernel selector and the dispatcher so the
two cannot disagree. On this GPU it turns the new path on at 5,376 tokens of cache and
hands shorter contexts back to the stock kernel. It reads the SM count from the device,
so it is a property, not a tuned constant.

The kernel applies at batch 2 or below. An earlier traffic model predicted it should win
up to batch 8. Direct measurement disagreed: at 54,016 tokens of cache the MMA kernel
costs a flat 812 to 838 µs per operation regardless of batch, while the vector kernel
starts at 713 µs and grows by about 222 µs per added token. The reason is achieved
bandwidth, not bytes moved. The MMA kernel streams at 621 GB/s through a multi-stage
asynchronous copy pipeline, while the vector kernel at 255 registers runs at low
occupancy and is latency-bound at 280 GB/s.

Validation: mean KL divergence against the unpatched kernel 0.003010 ± 0.000096, same
top token 98.009% of the time, perplexity ratio 0.999076. That is a different reduction
order, not a quality regression. All 2,970 flash-attention conformance cases pass. This
mattered, because upstream had **no** coverage for this exact shape: quantized cache with
head dimension 256 and six query heads per key/value head. The patch adds it.

### Patch 0004 — make the kernel-switch threshold an environment variable

`GGML_CUDA_MMVQ_NE11_MAX` caps the MMVQ batch threshold at run time on the quantized
dense path. It is off by default. At a cap of 3, measured at depth 0:

| tokens in step | stock | cap 3 | change |
|---:|---:|---:|---:|
| 1 to 3 | 25.0 / 27.8 / 32.5 | 25.2 / 27.7 / 32.0 | unchanged, correctly scoped |
| 4 | 39.06 | 35.78 | −8.4% |
| 5 | 43.14 | 36.21 | −16.1% |
| 6 | 49.46 | 36.41 | −26.4% |
| 8 | 61.46 | 36.84 | −40.1% |

Batches of 4 to 8 collapse onto a flat 36 to 37 ms line, which matches the predicted MMQ
curve. Mean KL divergence: 0.006325.

The knob is set per backend, not globally, because the right threshold depends on the
model. A blanket cap measurably hurt the `hauhau-gemma4-26b-a4b` backend, whose smaller
mixture-of-experts matrix multiplications genuinely prefer MMVQ at batch 4 to 8. The size
of that harm is disputed; see "Open items".

### Patch 0005 — teach the MMA kernel to read `q4_0` directly (image v7)

This removes the conversion found in stage 2 rather than working around it. The kernel
loads quantized values and dequantizes them inline, so the scratch F16 copy of the cache
never exists. Two measurements priced the work before anyone wrote it: running the same
kernel on an F16 cache put a hard floor of 8.70 ms per step on the saving, and an
isolated load-stage benchmark showed the quantized load plus inline dequantization cost
174.9 µs against 251.7 µs for the F16 load.

It beat that projection. At 54,016 tokens of cache, one binary switched by an environment
variable, with every control row matching at 1.00×:

| tokens in batch | old kernel | new kernel | speedup |
|---:|---:|---:|---:|
| 2 | 484.4 µs | 181.5 µs | 2.67× |
| 3 | 813.1 µs | 160.5 µs | 5.07× |
| 4 | 815.9 µs | 161.1 µs | 5.06× |
| 5 | 831.6 µs | 224.0 µs | 3.71× |
| 8 | 837.8 µs | 230.4 µs | 3.64× |

That saves 10.4 to 10.5 ms per verify step, against the 8.7 to 9.9 ms projected. The
data chose the gate: batch 2 and above. At batch 1 the new path measured 10% slower,
because about 40 µs of inline dequantization outweighs the vector kernel's single-column
deficit, so patch 0003 still serves batch 1. KL divergence against the conversion path:
mean 0.000000, maximum 0.000064, same top token 100% of the time. That is expected when
the same values are dequantized in a different place. All 2,994 conformance tests pass.

End to end on the 54k payload, this took the model from 58.8 to 66.8 t/s.

### Configuration — raise the draft length

Before the kernel-switch cap, `--spec-draft-n-max 4` was a trade: better at depth, worse
on short prompts. With the cap it wins everywhere. Measured end to end, greedy, 320
tokens generated:

| arm | `deep` (54k) | `short` |
|---|---:|---:|
| draft 2, stock kernel (old production) | 49.80 | 62.35 |
| draft 4 with cap 3 | 58.55 | 68.50 |
| draft 6 with cap 3 | 58.53 | 69.67 |

And at 1,000-token prompts, all arms measured in one block against the shipped kernel:

| arm | `mid1k` (code) | `mid1kprose` |
|---|---:|---:|
| draft 2 (old production) | 64.01 | 62.69 |
| draft 4, **no cap** | 60.77 | 59.82 |
| draft 4 with cap | 70.33 | 69.57 |

The middle row is the important one. With the same tree and the same arm, turning the
environment variable off makes draft 4 *slower than draft 2*. The variable turns a 5%
regression into a 10% gain. See "Two settings you must not change alone".

`--spec-draft-p-min 0.3` shipped briefly and was then removed. It had never been
benchmarked in combination with the cap; all its supporting evidence came from the
uncapped kernel. Measured afterwards it cost 10.8% on 1,000-token prose, with
non-overlapping ranges: the best repetition of the combination was worse than the worst
repetition without it. It also makes latency vary by about ±8%, because early stopping
interacts with state the MTP implementation carries between requests. Plain draft 4 is
bit-identical at temperature 0 and repeats within 0.12%.

## Stage 4 — new base, GPU draft sampling, draft length 5 (2026-08-16 to 2026-08-17)

**Image v9** moved the pinned llama.cpp from `62bf73d` to master `4df29be4f`. All five
patches re-applied, one of them rebased over an upstream server redesign. A prefill fix
to patch 0005 restricts the inline-dequant path to batches of 2 to 16, which returns
prompt-processing speed at depth to the pre-v7 level; v7 had lost 3.6% to 3.8% there.
Validation passed 62 of 62 and 2,994 of 2,994 flash-attention tests, with mean KL
divergence 0.000000 against v6, 67.0 t/s at 54k depth, and 68.4 t/s shallow.

Validation also caught a silent failure. Master enables backend sampling for DFlash
drafts, which conflicts with an older vendored patch and drops the `muse-glimmer-30b`
backend's draft acceptance to exactly 0. Nothing reported an error; the backend simply
lost its speculation. v9 worked around it with a command-line flag.

v9 also sets `reasoning_effort` to `medium`. The model's chat template defaults to
`xhigh`, which produces very long reasoning on trivial tasks; the community has measured
22,000 reasoning tokens on trivial prompts. Clients can override the value per request in
either direction. This is a deliberate quality-for-latency trade, unlike the kernel work,
which is numerically neutral.

Pass that value through the per-model environment list, not as a command-line flag.
llama-swap splits the command into shell words and strips the quotes from JSON, which
crashes the backend when it starts.

**Image v10** replaces the v9 workaround. A new patch makes the older patch's greedy fast
path defer to backend sampling, so `muse-glimmer-30b` now uses GPU draft sampling: 3.2%
faster on short prompts, 2.7% at 1,000 tokens, 3.0% on 7,000-token prose, with identical
output bytes, draft counts, and acceptance. The GPU sampler picks exactly the tokens the
host sampler picked.

Do not run the current `muse-glimmer-30b` command on an image older than v10. On v9 it
silently drops acceptance to 0.

**Draft length 4 to 5, on 2026-08-17.** The MMQ tile computes 8 columns whether or not
you use them, so a batch of 8 costs only 1.7% more than a batch of 2. The old draft-length
ceiling was acceptance economics measured before patch 0005 made verification cheap. A
fresh sweep on v10, same-block with four interleaved repetitions:

| payload | draft 4 | draft 5 |
|---|---:|---:|
| `mid1k` (code) | 70.5 t/s | 84.1 t/s (+19%) |
| `deep` (54k) | 66.8 t/s | 69.3 t/s |
| `short` | 68.4 t/s | 72.4 t/s |
| `prose7k` | 68.7 t/s | 69.5 t/s |

Draft lengths 6 and 7 lose. Draft 8 or more would cross into the next MMQ tile and cost
9% more. The change alters only the speculation configuration, so the output is lossless.

## Two settings you must not change alone

**If you change `--spec-draft-n-max`, change `GGML_CUDA_MMVQ_NE11_MAX` in the same
commit.** Draft length 5 is faster only because the environment variable is set. With the
variable unset or misspelled, draft length 4 is slower than the old draft length 2, at
60.8 against 63.7 t/s on a 1,000-token prompt. Nothing fails, nothing logs an error, and
the backend serves more slowly than it did before the change. Verify the variable on the
running process after any change, with the model loaded:

```bash
kubectl -n apps exec deploy/llama -c llama-swap -- sh -c \
  'tr "\0" "\n" < /proc/$(pgrep -x llama-server|head -1)/environ | grep MMVQ'
```

**Never lower `--ctx-checkpoints` on this model.** The recurrent DeltaNet state cannot be
truncated, so the server can reuse a prompt prefix only when a checkpoint exists to roll
back to. Without one it re-prefills from zero and reports no error. At 54k tokens that
turns a 0.26-second cache hit into a 56-second prefill. Raising the value above 32 gains
nothing: a real 55,000-token conversation used 3 of the 32 slots.

That prompt cache is the reason agentic clients see fast first tokens. This build enables
it by default and production passes none of its flags. Measured at 54k tokens:

| pattern | time to first token | with the cache off |
|---|---:|---:|
| cold prefill | 55.8 s | — |
| repeat the same prompt | 0.26 s | — |
| append a new 896-token turn | 1.44 s | — |
| another client interleaves, then return | 0.57 s | 57.0 s |
| edit the tail and retry | 0.98 s | 56.0 s |

Three concurrent 50,000-token conversations with no shared prefix all stay warm, using
3.4 GiB of the 8 GiB default. Do not raise `--cache-ram` above about 8 GiB without also
raising the pod memory limit.

## Fine-tuning: why we did not

Fine-tuning changes behavior. It does not raise tokens per second. Speed comes from
quantization, kernels, KV-cache choices, and speculative decoding, which is where every
measured gain above came from.

**This GPU cannot run the recommended method.** Unsloth reports about 56 GB of VRAM for
BF16 LoRA on the dense Qwen3.5-27B model, and roughly four times that for full
fine-tuning. Unsloth also discourages 4-bit QLoRA for that family, because it shows
larger-than-normal quantization differences. Qwen3.8 is built on the Qwen3.5
architecture, so applying that warning here is a conservative inference, not a measured
Qwen3.8 result. A 24 GB QLoRA attempt would need short sequences, batch size 1, gradient
checkpointing, probably CPU offload, and very new framework support. It would be slow,
and it would choose the method the nearest guidance warns against. The host's system RAM
does not turn a 24 GB card into a 56 GB training card.

Do not train from scratch. The 27B checkpoint is Apache-2.0, so fine-tuning and
redistribution are permitted, but that is not the constraint. Compute is.

The recommended path, in order:

1. Compare newer GGUF conversions. **Done** — see stage 1.
2. Build a contamination-controlled evaluation set of 300 to 1,000 real tasks, with a
   temporal holdout, deduplicated splits, and labeled success criteria. **Not started.**
   This blocks everything after it.
3. Rent one 80 GB accelerator for a BF16 LoRA SFT pilot on the language layers only.
   Freeze the vision encoder and projector. Start at LoRA rank 16 or 32, batch size 1
   with gradient accumulation, 2,000 to 4,000 token sequences, one epoch, with evaluation
   at every checkpoint.
4. Add offline preference optimization only if supervised fine-tuning fixes formatting
   but the model still chooses poor strategies. Defer reinforcement learning entirely; it
   needs far more generation capacity and rewards shortcuts when the grader is weak.
5. Merge the adapter into the original BF16 checkpoint, preserve the tokenizer and chat
   template, convert to GGUF with a build that supports Qwen3.8, and serve it under a new
   llama-swap ID such as `qwen3.8-27b-homelab-lora-v1`. Never overwrite `qwen3.8-27b` for
   a trial.

**Train behavior, not facts.** The useful targets are tool selection and exact argument
schemas, diagnosis of the GitOps repository's k3s, Flux, storage, Caddy, and llama-swap
patterns, concise Portuguese and English operational answers, recovery after tool errors,
and coding tasks from real repositories. Use retrieval for anything that changes.
Fine-tuning is not a database and makes facts harder to update.

**Treat the MTP draft head as unmatched after any weight change.** It was trained with
the base model, so acceptance may fall even though verified speculative decoding
preserves the main model's output distribution. Qualify a fine-tune with speculation
disabled first.

Agree the promotion gate before training, not after: at least 10 points gained on the
targeted failure suite, no more than 2 points lost on the general regression suite,
tool-call schema validity at or above 99%, no vision regression, no new secret-leak,
destructive-action, or fabricated-verification failures, acceptable latency with no
out-of-memory failure at the advertised context, and reproducible results across at least
three runs.

The likely end state is a portfolio, not one replacement: the proven quantization as the
long-context and vision baseline, a domain adapter for homelab and agent work if it
clears the gate, and the untouched base for everything the adapter regresses.

## Rules that generalize

- **Content decides draft-length economics, not context depth.** At the same depth and
  generation length, code-grounded generation ties or wins with longer drafts, while
  prose loses about 7%. Acceptance is indistinguishable until draft position 2 and
  separates after it. Depth scales the size of the effect; it never flips the sign.
- **`--spec-draft-p-min` inverts once verification becomes cheap.** It stops drafting to
  save verify cost, but when rejected positions are nearly free it forfeits accepted
  tokens instead. It was never free: stopping at a position has already paid for the
  draft model's work that produced the rejected token.
- **The kernel-switch threshold depends on the model.** Upstream's flat constant of 8 is
  wrong for a 27B dense Q4_K matrix multiplication on this card and right for the smaller
  mixture-of-experts model on the same card. Any fix has to be per model, which is why the
  patch adds an environment variable rather than changing the constant.
- **Mixed key and value cache types silently disable GPU flash attention.** With `q4_0`
  keys and `q8_0` values, llama.cpp selects no flash-attention kernel: prompt processing
  falls to 39% of production and the run drops to the CPU at 0% GPU use. `llama-bench`
  still prints `fa = 1`, because it reports the flag you requested, not the kernel it
  chose. Setting keys to F16 and values to `q4_0` to save VRAM gets no warning either.
- **F16 and `q8_0` caches do not help on Ampere.** `q8_0` stays on the same redundant path
  with 1.9 times the bytes, so it is worse than `q4_0`. F16 reaches the faster path but
  needs 8.4 GB at 131k and does not fit beside the draft model and the projector.
- **Compare milliseconds per step, not tokens per second, across a numerics change.** A
  kernel change perturbs the logits, so two arms sample different tokens and hit different
  acceptance rates, and raw throughput then compares luck as much as speed. Normalizing
  turned an apparent 2.9% loss into a correctly attributed 5.7% gain, and an apparent 1.5%
  loss into measured parity.
- **Measure sustained work, and always include a control in the same block.** A single
  small forward pass times the GPU's clock ramp out of idle: noise is 9% to 28% on
  single-pass rows against 0.05% to 0.3% sustained, and repeating the pass does not fix it,
  because every repetition pays the same ramp. One cross-block comparison here produced a
  7% regression that never reproduced.
- **Gate a quality check so that it actually touches the kernel.** Generate the divergence
  baseline at the same micro-batch size as the test. A run above the patched kernel's gate
  reports exactly 0.00000 divergence at 100% same-top-p, which looks perfect and means
  nothing. A same-top-p slightly below 100% is the evidence the run exercised the new code.
- **Check whether production is idle with `GET /running`, never `GET /upstream/*`.** The
  second is proxied and loads the model: it answers in 300 µs when the model is resident
  and takes 10 seconds while cold-loading 23 GB when it is not. A check built on it wakes
  the service it is checking. That cost one experiment its GPU.
- **Verify VRAM from a real run at the real context size.** `llama-bench` has no draft
  model, no projector, and sizes the context to the test, so its numbers do not describe
  production.

## Tried and rejected

- **Upstream master, before v9.** Bit-identical output, 5.6% slower on short prompts. The
  premise that the pinned build lacked backend sampling was wrong.
- **Chained speculation from an unmerged pull request.** 6% to 12% slower on a realistic
  prompt, acceptance fell from 0.829 to 0.602, and greedy output stopped being
  reproducible.
- **CUDA graph optimization.** Within noise on both payloads.
- **A vLLM W4A16 recipe.** The requantization reproduced exactly, but at the recipe's own
  memory setting the context caps at 124,800 tokens, below production's 131,072. Cold
  start takes 4 to 5 minutes, it needs a new 8 GB image, and its attention library
  compiles on the first request, so the server reports healthy and then fails every
  request if the compiler is missing.
- **Raising the vector-kernel gate to batch 8.** The vector kernel is latency-bound at
  280 GB/s against the MMA kernel's 621 GB/s on the same shape, which moves the crossover
  from a predicted 8.1 to 3.4.
- **Keeping an incremental F16 shadow of the cache.** 3.54 GB at 54k tokens and 8.59 GB at
  131k, against about 1 GiB of headroom.
- **Draft length 6, at the time.** 23,650 MiB against a 23,400 MiB ceiling, and no gain.
- **`--parallel 2`.** 620 MiB more, over the ceiling, and it halves each client's window to
  65,536 tokens to save 0.07 to 0.10 s per client switch.
- **`--slot-save-path`.** Restore reports success and 54,468 tokens restored in 251 ms, and
  the next request still re-prefills for 56 seconds. The saved file carries no checkpoints
  and no draft state.
- **`--cache-reuse`.** Forced to zero at startup whenever a vision projector is loaded.
- **DFlash, EAGLE-3, and DSpark draft models.** Open upstream defects, and no trained
  checkpoint exists for this target.
- **A Q8_0 MTP draft head.** 3.16 GB more than the embedded baseline.

## Open items

- **Patch 0003 was never submitted upstream.** A rebased branch is prepared and passes
  5,191 flash-attention conformance cases on master, and a duplicate search found no
  competing pull request. Submission is a manual step for a person: `ggml-org/llama.cpp`
  forbids agent-created pull requests and machine-written pull-request text.
- **No task-quality evaluation exists.** Bartowski and Unsloth have never been compared on
  task pass rate. Step 2 of the fine-tuning path is the same missing piece, so both tracks
  are blocked on one artifact.
- **Three figures in the campaign record are unverified.** The two 7,000-token arms, the
  58.8 t/s deep figure, and the no-speculation pair of 28.2 to 33.3 t/s survive only as
  campaign summaries, with no measurement report behind them. Re-measure them before
  building on them. Every other number in this document traces to a preserved report.
- **The gemma4 baseline never reproduced.** Two sessions measured its short payload at
  236 t/s and at about 104 t/s, most likely a payload or generation-length difference. The
  claim that a blanket kernel-switch cap costs that backend 34% of its decode rests on the
  unreproduced baseline, and it was measured on a hard-capped build rather than the shipped
  environment-gated one. It changes no shipped decision, because that backend fails the
  ship rule either way on a separate regression, but re-check before enabling the variable
  for it.
- **The production quantization already embeds an MTP head** at the same precision as the
  separate draft file. Dropping `--model-draft` could save about 1.6 GB of VRAM with no
  change in speed. Not tested.

## How to reproduce any of this

Follow the rules above, and add the two steps they do not cover. Both exist because every
arm competes with a live production service for the only GPU in the machine.

1. **Take an exclusive lock that records the owning process ID, not just a name.** A name
   cannot outlive its holder. One agent deadlocked against its own orphaned waiter for 15
   minutes.
2. **Gate on idle before you claim the GPU:** no slot processing, GPU below 5%, no new
   requests, held for two minutes. Then unload the model and confirm the GPU holds less
   than 1,000 MiB.

Then run each arm in a container using the exact production command as the base flag set,
send one warmup request, and measure 2 to 4 repetitions. Fixed-length speculative arms are
bit-deterministic and agree within 0.2%. Anything with a variable draft length is not, and
needs four sequential repetitions.
